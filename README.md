# Tentacula

Приложение Tentacula работает как терминирующий компонент. Когда клиенту нужно обратиться к удалённой системе, доступ к
которой напрямую невозможен или не рекомендуется, на разрыв между клиентом и сервером устанавливается Tentacula. По
HTTP/HTTPS-протоколу клиент передаёт данные необходимые для запроса (данные авторизации и атрибуты запроса), на заранее
опубликованную "Присоску". Присоска уже с терминирующего компонента обращается на конечный сервис (протокол между
Tentacula и сервером определяется в функции самой Присоски). После того как сервер даст ответ, терминирующий компонент
ретранслирует его клиенту в режиме стриминга.

Tentacula поддерживает 3 механизма взаимодейтсвия:

1. suсkers (присоски) - эндпоинт использующий POST-протокол, с заранее описанными требованиями и функционалом, который
   будет исполнен с сервера Tentacula. Предусмотрены встроенные эндпоинты для взаимодействия с DS;
2. composition (сочленение) - эндпоинт передачи клиентского запроса следующему за ним эндпоинту (в том чсиле и другим
   Tentacula);
   чтобы последняя в очереди Tentacula обратилась к серверу;
3. schedulers (планировщик) - механизм автозапуска заданий, которые необходимо исполнять с сервера Tentacula.
   Предусмотрен встроенный планиврощик исполнения задания к DS, когда планировщик ожидает задание в таблице БД;
4. logs - получение логов Tentacula.

## Авторизация на эндпоинтах

Эндпоинты требуют использовать один из способов аунтификации:

- анонимный (без проверки пользователя);
- по сертификату (проверка по полю subject);
- по LDAP в сочетании авторизации на сервере DS и наличию членства в группе.

Если выбрана авторизация по сертификату или LDAP, то в параметрах `LIST_OF_PERMITTED` конфигурационного файла и `access`
пользовательских присосок требуется указывать список, кому разрешён доступ.

## Установка

Пакет Tentacula подготовлен для установки в оффлайн режиме.
В папке `packages` указаны необходимые зависимости и готовые Conda-среды для Windows и Linux.
Настройка службы uvicorn происходит вне дистрибутива.
В файле `config.cfg` производится настройка приложения (в том числе формирование конфигурационного файла для NGINX с
рекомендуемыми параметрами).

### Установка зависимостей

Перед настойкой приложения требуется установка следующих зависимостей:

```
apt-get update && apt-get install -y \
krb5-user \
supervisor \
nginx
```

NGINX требуется если он будет использоваться как проксирующий элемент.

### Подготовка рабочей области

Рабочая область приложения структурируется следующим образом (на примере относительно пути `/app/tentacula`):

- Папка приложения `app` располагается в корне рабочей области;
- В корне рабочей области обязательно должны быть конфигурационный файл `config.cfg`;
- Сертификаты, папка с присосками и папка с планировщиком могут быть переопределены в любое место через `config.cfg`;

### Подготовка среды Conda

Для работы через среду конда, на UNIX-системах необходимо корректно развернуть Conda-Pack. Папка с распакованным
Conda-Pack'ом является рабочей средой и далее её нужно будет указать в параметрах конфигурирования.
Подготовка среды (на примере относительно пути `/app/tentacula`, таким образом рабочей средой будет
`/app/tentacula/conda_env`):

```
mkdir /app/tentacula/conda_env
tar -xzf tentacula.tar.gz -C /app/tentacula/conda_env
rm tentacula.tar.gz
```

### Настройка переменных окружения и запуск службы

Переменные окружения необходимо для работы (обратите внимание на область среды):

```
ENV PATH="/app/tentacula/conda_env/bin:$PATH"
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
```

Строка запуска приложения как ASGI web-сервера (запускается из области приложения `/app/tentacula`):
`/app/tentacula/conda_env/bin/conda-unpack && uvicorn app.main:app --host 0.0.0.0 --port 8000`

## Настройка среды

Переменные среды читаются либо из окружения, либо из config.cfg
Приоритет чтения:

1. Переменные окружения;
2. Конфигурационный файл `config.cfg`;
3. Значение по умолчанию, если есть.

Переменные окружения генерируются по формуле: `TENTACULA__<РАЗДЕЛ>__<ПЕРЕМЕННАЯ>` (всё буквы заглавными)

Для значений допустимо указать в начале `cat ` (с пробелом), для чтения значения из файла:

- `app` -> `DB_ASYNC_URL`;
- `app` -> `SECRET_KEY`.

Параметры изначально ожидают ссылку на файл, поэтому `cat ` не указывается:

- `composition` -> `TRANSIT`;
- `schedulers_ds` -> `TRANSIT`.

## Описание функций

Для активации функций производится в файле `config.cfg`.

### API логов

Включается параметром `APP__LOGS_API_ENABLED`.

API считывает из конфигурационного файла места логов web-сервера и приложения, чтобы читать и выдавать их по запросу.
API лог доступен по адресу `/logs`. Принимаемые параметры запроса:

- `search_depth` - Включение поиска во вложенных папках (по умолчанию False). Актуально, если логи будут переноситься во
  вложенные папки относительно параметра указанного в конфигурации;
- `source` - Источник логов. Обязательный параметр. Принимает либо одно значение как строку, либо массив.
    - `web_access` - логи веб сервера из блока `access_log`;
    - `web_error` - логи веб сервера из блока `error_log`;
    - `api` - логи приложения;
- `time_start` - Фильтр по начальной дате поиска (больше или равно значению) в формате ISO-8601. Опциональный параметр;
- `time_end` - Фильтр по конечной дате поиска (меньше значения) в формате ISO-8601. Опциональный параметр;
- `s_id` - Фильтр по ID-сессии. Опциональный параметр.
  При использовании `time_start` и `time_end` указанное значение воспринимается как строка и фильтрация принимается по
  правилу сортировки UTF-8. Поэтому нужно учитывать, что веб-сервер не указывает миллисекунды и все даты лога
  указывается с указанием часового пояса (по умолчанию гринвич).
  Пример указания даты для поиска (не указаны миллисекунды и часовой пояс): `2026-10-10T09:58:47`.

### API переадресации запросов

Включается параметром `COMPOSITION__ENABLED`.
Позволяет использовать API Tentacula на удалённом сервере с Tentacula. Запроса направляется на API переадресации
запросов и содержит входные данные, которые должны быть использованы для запроса, который будет производиться с
удалённой Tentacula.
API доступен по адресу `/composition`.
Параметры:

- `url_` - Доменный адрес, на который будет направлен запрос (пример: `http://localhost:8080`);
- `path_` - Путь к ресурсу, который будет добавлен к доменному адресу;
- `json_` - Словарь с данными, которые будут добавлены к запросу в блок `json`.
  Фактически, когда Tentacula получит запрос на `/composition`, сама Tentacula попробует инициировать POST-запрос на
  указанный адрес со входными параметрами до удалённой Tentacula.
  Переадресация запросов поддерживает параметр `transit`, позволяющий хранить на Tentacula, набор данные, которые будут
  обогащать изначальный запрос.
  Если в конфигурационном файле будет указан `COMPOSITION__TRANSIT`, то параметр `url_` будет считаться ID, по которому
  в файле транзита будет производиться поиск данных. Когда по ID, данные будут найдены, поля`url_` и `json_` будут
  заменяться.

Пример:

Исходный запрос. По плану требуется в DS изменить имя пользователя, но с ближайшей Tentacula "A" нет доступа до DS, но
со следующей Tentacula "B", доступ есть

```
'https://localhost:8080/composition',
json={
    'url_': 'EXAMPLE',
    'path_': '/ds/set_user',
    'json_': {
        'host': '192.168.0.2'
        'identity': 'user_01',
        'display_name': 'New value'
    }
}
```

Когда запрос доходит до Tentacula "B", запрос происходит по следующим этапам:

1. Если значение из поля `url_` не найдено в файле из `COMPOSITION__TRANSIT`, то доменным именем запроса считается
   значение `url_`;
2. Если значение из поля `url_` найдено как ключ в файле из `COMPOSITION__TRANSIT`:
    1. Исходное значение из `url_` подменяется на то, что указано в аналогичном параметре в файле транзита. В файле
       транзита в `url_` либо один домен, либо массив доменов и тогда Tentacula "B" будет пытаться отправлять запрос на
       последующие в списке, если первая вернула "httpx.ConnectError";
    2. Если в файле транзита есть блок `json_` и в нём есть ключ, которого нет в исходном запросе, этот ключ и его
       значение добавляются.

Файл транзита содержит данные:

```
{
  "EXAMPLE": {
    "url_": [
      "https://tent.local"
    ],
    "SSL_CA_CERTS": "/app/tentacula/certs/ca.crt",
    "SSL_CERTFILE": "/app/tentacula/certs/tent_b.crt",
    "SSL_KEYFILE": "/app/tentacula/certs/tent_b.key",
    "json_": {
      "login": "admin",
      "password": "123456"
    }
  }
}
```

Тогда финальный запрос, который будет инициирован с Tentacula "B", будет сопровождаться сертификатами, которые
расположены на Tentacula "B" и выглядеть следующим образом:

```
'https://tent.local/ds/set_user',
json={
    'login': "admin',
    'password': '123456',
    'host': '192.168.0.2'
    'identity': 'user_01',
    'display_name': 'New value'
}
```

Финальный запрос идёт по сформированному URL и тело запроса добавлены параметры 'login' и 'password', которых не было в
изначальном запросе.

### API пользовательских присосок

Включается параметром `SUCKERS__ENABLED`. Пользовательские присоски доступны по адресу `/sucker/<имя_присоски>`.
Позволяют опубликовать пользовательские присоски. Пример оформления приведён в папке `suckers`.

### API присосок для работы c DS

Включается параметром `SUCKERS_DS__ENABLED`. Доступны по адресу `/ds/<имя_функции_ds>`.
API совпадают с функциями описанными в классе `app.ds.DSHook`.
Для упрощения работы с DS напрямую, DS через Tentacula и DS через scheduler Tentacula, рекомендуется использовать класс
`app.sds.SDSHook`.

### Пользовательские шедулеры

Включается параметром `SCHEDULERS__ENABLED`. Позволяет описать и подключить пользовательскую присоску.
Пример оформления приведён в папке `schedulers`.

### Шедулер для исполнения заданий из таблицы в DS

Включается параметром `SCHEDULERS_DS__ENABLED`. Позволяет публиковать задания для работы с DS в SQL-таблице, куда будет
записан ответ.
Поддерживает транзит аналогично "API переадресации запросов".

Для упрощения работы с DS напрямую, DS через Tentacula и DS через scheduler Tentacula, рекомендуется использовать класс
`app.sds.SDSHook`.
